# مراجعة قبول مستقلة لإغلاق مخاطر WebRTC

المراجع: `close_acceptance`، 21 أكتوبر 2026. المرجع السابق: [approval-final.md](approval-final.md).
ملكية المراجع تقتصر على هذا التقرير و[دليل المراجعة](closure-acceptance-review.json)؛
لم يعدّل المراجع المنتج أو أدوات الوكلاء، ولم يشغّل حملًا منافسًا.

**المراجعة مكتملة: لا finding برمجي مانع متبقٍ في الإصلاحات المحددة. القرار: غير جاهز للاعتماد الإنتاجي الكامل؛ أُغلقت المخاطر المحلية ضمن حدود الدليل، وتبقى فجوات القبول الميداني ومسار التطبيق الكامل.**

## معايير الإغلاق

- يحتاج فشل PCM إلى إعادة إنتاج مع أدلة ICE/RTP وسبب يفسر النتيجة، ثم تشغيل حديث
  على الإعداد المصحح. connect/publish أو الجولة السابقة ذات الربط الأوسع لا يكفيان.
- يحتاج تغير واصفات الملفات إلى تصنيف نوعها ومالكيها وفترة الاستقرار ومقارنتها
  بعد warmup؛ لا يثبت العدد وحده تسربًا أو نفيه. خروج العملية الطبيعي ليس قياسًا
  لتحرير مواردها أثناء بقائها حية. سلامة ملفات SDK تُراجع مقابل أصل موثوق دون
  فقد تعديلات المستخدم أو إعادة ضبط عامة للمستودع.
- يحتاج heartbeat إلى اختبار الطلب الجاري والمغادرة وunmount وتغير الغرفة،
  وإثبات الإلغاء ومنع استجابة قديمة أو polling لاحق، مع بقاء كتابة leave ذات 45s.
- لا تُستبدل إعادة تشغيل الاختبارات الحرجة بنتائج Turbo cache. نتائج المحاكاة
  وnative SFU والمتصفح والأجهزة الحقيقية تُذكر كلٌّ على حدة.
- لا تغلق نتيجة HTTP ونتيجة native SFU منفصلتان رحلة التطبيق الكاملة عبر بوابة
  القبول وإبطال الصلاحيات. إنتاج التطبيق يستخدم `livekit-client`؛ harness الأصلي
  يستخدم `@livekit/rtc-node`، لذلك لا يُنسب خلل أحدهما للآخر دون دليل.

## الفحص المستقل الأولي

جرد الـ83 المتجاوزة راجعه المراجع من ملف AST بالأسماء الموسعة: 69 للممالك والخريطة،
10 لـfastest/Redis، و2 OpenClaw، و2 Blender. لا حالة مباشرة لـLiveKit PCM أو
heartbeat أو بوابة الغرفة داخل هذه القائمة. أهمية بعض الاختبارات لأمن الألعاب
لا تجعلها دليلًا على مسار صوت غير منفذ.

بصمة Desktop CSS عند بدء المراجعة تطابق الدليل السابق:
`b7da25d79f4a933a6b4ce006e5faaff79e6a2528b6f62cf858d14a26dc6a4e82`.
حُفظت أيضًا بصمات mobile/shared CSS وspec والنقل وعميل HTTP في JSON للمقارنة بعد الدمج.

إذا تغير عقد إلغاء heartbeat، يجب تحديث اختبار lifecycle القديم الذي يثبت ذيل
10s إلى السلوك الجديد وإعادة تشغيله؛ ترك assertion القديم أو عدم تشغيل المجموعة
ليس إغلاقًا للفجوة. أُبلغ المنسق بذلك قبل الدمج.

## مراجعة السبب الجذري ومقياس PCM

أعاد المراجع تحليل PCM المحفوظ مستقلًا باستخدام NumPy FFT مع نافذة Hann، دون
تشغيل SFU إضافي: القمم كانت 662.22/662.22/665.22Hz للطرف المتوقع 660،
و437.78/437.78/435.56Hz للطرف المتوقع 440. بقي 95.57–98.66% من الطاقة داخل
±25Hz. عداد عبور الصفر أبلغ في بعض العينات 790 و511Hz رغم وجود الإشارة الصحيحة.
النتيجة تؤيد سببًا في أداة القياس: رفض إشارة مفكوكة صحيحة، لا غياب PCM أو فشل ICE.
[العينات الخام](closure-webrtc-pcm-diagnostic.json) ونتائج الحساب المستقل داخل JSON المراجعة.

راجعت `webrtc-audio-metric.mjs` واختبارات التحكم: احتفظ الإصلاح بـ15 إطارًا على
الأقل، وRMS>300، وتسامح ±25Hz؛ وأضاف شرط تركّز طاقة لا يقل عن 80% في نطاق الهوية.
الصمت والتردد الآخر و880Hz والضوضاء والإشارة المنخفضة والإطارات القليلة تُرفض.
احتُفظ بعبور الصفر كتشخيص؛ لم يُضعف التحقق إلى مجرد وجود أي طاقة صوت.

راجعت [التنفيذ المصحح](closure-webrtc-verification.json): 11 معيارًا ناجحًا داخل
سيناريو واحد، عمليتان مستقلتان خرجتا طبيعيًا برمز 0، وصفر مشاركين وrelay بعد
التنظيف. [إعداد البيئة](closure-webrtc-environment.json) يثبت ربط UDP والإشارة على
127.0.0.1 فقط، ونفس إعداد النقل قبل إصلاح أداة القياس وبعده. لا تغيير لصوت المنتج.

## مراجعة heartbeat

راجعت signal صاحب دورة polling وتنظيفه عند المغادرة وunmount وتغير الغرفة،
وقراءة fallback. الاستجابة القديمة محجوبة، والإلغاء لا يصير خطأ واجهة أو إعادة polling.
مراجعة مستقلة اكتشفت سباقًا إضافيًا في `refresh` المرتبط بأحداث الوسائط: `finally`
قديم كان يستطيع جدولة closure للغرفة السابقة بعد تغير المالك. أصلحه الوكيل بعد
اختبار RED بمعرّف generation وحارس controller identity. قرأت الاختبار الجديد
الذي يبدّل الغرفة ويجدول تحديث المالك الجديد قبل تسوية رفض القديم، ثم يسلّم
الاستجابة القديمة، ويتحقق من بقاء المالك الصحيح.

[قبل الإصلاح](closure-heartbeat-before.json)، [سباق refresh قبل الإصلاح](closure-heartbeat-refresh-race-before.json)،
و[الثمانية بعد الإصلاح](closure-heartbeat-after.json) محفوظة. لم تتغير مهلة كتابة
leave؛ الاختبار يغطي عدم إلغائها عند 44,999ms وإلغاءها عند 45,000ms مستقلًا عن
إلغاء القراءة. إلغاء HTTP في العميل لا يثبت إلغاء العمل الذي بدأ على الخادم.

## سلامة SDK والتجاوزات

راجعت [فحص SDK](closure-sdk-integrity.json): 224/224 ملفًا مطابقًا لفهرس pnpm
المرتبط بـSRI في lock، ولا writes أو patch. لا استعادة أو reinstall مبرران عندما
تكون النسخة مطابقة أصلًا. المقارنة لا تدعي تنزيل tarball جديدًا.

[probe SDK](closure-sdk-runtime.json) يفسر زيادة runtime أولية مستقرة من 27 إلى
35 FD: أربعة eventpoll واثنان eventfd واثنان Unix sockets، بلا TCP/UDP. لم تتكرر
الزيادة مع ثلاث دورات AudioSource. هذه النتيجة وحدها لا تفسر جميع FD الغرف؛
يجب قراءتها مع الاستقرار المشترك النهائي، ولا تُنسب مباشرة لمكتبة المتصفح.

[جرد التجاوزات](closure-skips-inventory.json) و[التنفيذ](closure-skips-execution.json)
يفصلان 81 اختبارًا أعيدت فعليًا دون Turbo cache عن اختباري Blender غير المنفذين.
المصدر لم يتغير؛ بصمات 12 ملفًا قبل وبعد موجودة في الدليل. الأدلة تشمل حذف
حاويتَي PostgreSQL وRedis الخاصتين دون حذف موارد مشتركة.

## مراجعة الاستقرار والموارد

راجعت [جولة الاستقرار](closure-stability-result.json) ذات 12 دورة و3 قطوع فعلية
لـWebSocket، و[تقريرها](closure-stability.md). ثمانية معايير داخل سيناريو واحد نجحت؛
ليست ثمانية unit tests. عادت العضوية والعدادات المرصودة إلى حدودها بعد كل مغادرة،
وتوقف المصدر المولد قبل disconnect، ونجح فحص الصمت بعد 250ms. هذا ليس قطع ICE
أو قياس توقف ميكروفون جهاز فعلي.

قارنت FD من الدليل نفسه: وصل A إلى 167 في الذروة ثم 70 في الدورة 12، وبعد
المغادرة والاستقرار صار 58، ثم 43 بعد إسقاط المرجع التشخيصي دون GC؛ GC لم يخفضه
أكثر. B استقر عند 39 بلا UDP بعد المغادرة. الأربعة UDP الأخيرة في A تتصل جميعًا
بـ`172.31.1.29:53`، كما يثبت الحقل الخام `remote=1D011FAC:0035`، وليست مقابس وسائط
أو اتصالًا بـ17882. راجعت كذلك [تصنيف sockets](closure-sdk-socket-analysis.json):
كل الـ19 UDP عند الاستقرار الأول كانت إلى DNS نفسه، لا SFU. ليس انخفاضها أثناء
إسقاط المرجع تجربة تحكم تثبت سببية المرجع؛ ولا نعرف أسماء الاستعلامات أو عمرها
من هذه اللقطة. ليست مقارنة baseline البارد مقياسًا صالحًا لكل موارد runtime.

تمييز التهيئة الأولى وموارد runtime ومقابس DNS يفسر سبب قصور
الاستنتاج السابق من العد وحده. لم يرصد السيناريو نموًا دائمًا لاتصالات الوسائط،
لكنه لا يثبت خلو كل native heap أو يضع حدًا لزمن اكتمال كل finalizer/DNS. لا أوصي
بتعديل مكتبة المتصفح أو فرض GC على المنتج بناءً على هذه البيانات.

التحذيرات الثلاثة عن مرشحي ICE متأخرين ذوي ufrag قديم محفوظة في
[دليل التنظيف](closure-webrtc-cleanup.json) ولم تُحذف من التقرير. نجحت معايير
التعافي الثلاثة؛ الرسائل وحدها لا تثبت عطلًا إنتاجيًا أو فشل السماع.

## إعادة الاختبارات بعد الدمج

قرأت [الجولة الإضافية النهائية](closure-final-lifecycle-tests.json): **16/16**
ناجحة، بلا فشل أو تجاوز، وتشمل الثمانية heartbeat والثمانية lifecycle كاملة؛
ليست إعادة الحالة المعدلة وحدها. ملف [الموارد](closure-lifecycle.json) الجديد
يؤكد الإلغاء الفوري للقراءة وصفر deadline متبقٍ دون الكتابة على الأدلة التاريخية.

قرأت [الجولة الشاملة النهائية](closure-final-suite.json): **3417 ناجحًا، صفر
فشل، 103 متجاوزة** خلال 6m25.164s. منها 2814 نجاحًا حديثًا و603 من cache؛
التجاوزات 93 حديثة و10 cache. ملفات الصوت الحرجة الـ11 نفذت فعليًا ضمن web
fresh، ومنها AudioSession وProvider وعميل الطلبات وadmission وLiveKit وHTTP
وevents-route وwebhook. لا نعد replay لحزم أخرى إعادة تنفيذ لهذه الاختبارات.

تحققت مستقلًا من SHA256 لسجل الجولة الكامل وملفات الاختبارات الحرجة الـ11
وملف `voice-room.tsx` بعد الجولة؛ كلها تطابق metadata. كذلك بقيت بصمات Desktop
وmobile/shared CSS وspec المرئي و`voice-client.ts` و`audio-session.tsx` كما كانت
عند بدء المراجعة. لا نقل صوت أو مهلة 45s تغيرا، ولا حاجة لمصفوفة متصفح كاملة
لمجرد تعديل effects لا تمس DOM/CSS.


قرأت سجل البناء النهائي: اكتمل compile وTypeScript وprerender، وانتهى الأمر
بنجاح وفق نتيجة المنسق. فحص ESLint للملفات المتأثرة/config انتهى برمز 0، وسجله
خالي من الأخطاء. بصمات السجلين محفوظة في JSON المراجعة. تحققت قراءةً من بقاء
`permissionWrite ? 45_000 : 10_000`، ومن إغلاق منافذ الموارد المملوكة TCP/RTC UDP.
لا اختبارات إضافية مكلفة أو إعادة جولة ناجحة مطلوبة من هذه المراجعة.

## القرار المستقل

**غير جاهز للاعتماد الإنتاجي الكامل؛ جاهز للانتقال إلى القبول الميداني للتدفقات
غير المنفذة.** أُغلق رفض PCM الصحيح في أداة الاختبار، وثبتت سلامة SDK وكون UDP
النهائية DNS وليست صوتًا متروكًا، وأُصلح إلغاء heartbeat/refresh وسباق المالك القديم
بتغطية RED/GREEN وإعادة اختبار حديثة بعد الدمج. لا ضرورة مثبتة لتغيير نقل الصوت
أو مهلة المغادرة، ولا عيب برمجي حرج متبقٍ مثبت في نطاق الإصلاح المراجع.

ما لم يُنفذ ويبقى خارج هذا القرار:

- رحلة browser AudioSession عبر بوابة قبول التطبيق وSFU وإبطال صلاحيات الغرفة
  كاملة بصوت حي؛ الأدلة الحالية تختبر طبقات منفصلة.
- صوت الجهازين وميكروفوناتهما وسماعاتهما ولوحة مفاتيح جوال فعلية.
- NAT/TURN وقطع ICE وشبكات المستخدمين المختلفة.
- ضمان خلو heap/native memory طويل الأجل أو حد عمر DNS؛ السيناريو المحدود
  لا يثبت هذه الضمانات. لا تُحوّل بقايا runtime/DNS إلى عيب browser SDK دون دليل.

إلغاء القراءة يحدث تزامنيًا عند تغيير المالك؛ تُنظف مهلة HTTP عند تسوية الإلغاء
في `voiceRequest.finally` دون انتظار 10s. كتابة leave مستقلة بـ45s، وإلغاء fetch
لا يلزم منه إلغاء عمل الخادم. لم تُنفذ أجهزة حقيقية، ولم تمنح هذه المراجعة موافقة
على Push أو نشر أو قبول مخاطر إنتاج نيابةً عن المستخدم.

راجعت النسخة المركزية النهائية [approval-final.md](approval-final.md) بعد تعبئة
نتائج الجولة والبناء والفحوص: لا placeholders أو روابط أدلة محلية مفقودة، والقرار
وحدود الإثبات متفقان مع هذه المراجعة. بصمة تلك النسخة محفوظة في JSON المراجعة.
