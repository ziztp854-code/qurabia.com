# إغلاق تحقيق PCM في WebRTC المعزول

التاريخ: 21 أكتوبر 2026. المراجع: `close_webrtc`.
المرجع: [قرار القبول السابق](approval-final.md) و[نتائج النقل التاريخية](approval-webrtc.md).

**النتيجة: الخلل المثبت في إعادة الإنتاج هو أداة تقدير التردد داخل الاختبار، وليس انقطاع PCM أو فشل ICE.**
بعد إصلاح أداة القياس فقط، نجح السيناريو الكامل المعزول حديثًا **11/11 معيارًا**
في 9.41s. لم يتغير منطق صوت التطبيق أو مهلة المغادرة 45 ثانية أو إعداد نقل SFU.
لا يحل ذلك محل اختبار مسار التطبيق الكامل أو الأجهزة الحقيقية.

## السبب الجذري والأدلة

الشرط القديم `goodTone` كان يتطلب 15 إطارًا وRMS>300 وترددًا ضمن ±25Hz، لكنه
قدّر التردد بعدّ عبور الصفر في PCM المفكوك. عبور الصفر لا يساوي التردد الغالب
عند وجود تشوه/طاقة إضافية حول الصفر. لذلك رسالة الانتظار «لم يرصد PCM 660Hz»
كانت أوسع من الحقيقة: قد تصل إطارات قوية بالتردد الصحيح ويرفضها هذا المقدّر.

نفذنا ثلاثة probes قصيرة تضيف معلومة مختلفة: مسار مباشر، ثم relay مطابق، ثم
حفظ PCM الخام من relay للمقارنة المستقلة. في جميعها وصل PCM بينما ظهرت تقديرات
عبور صفر خارج ±25. [الدليل المباشر](closure-webrtc-reproduction.json)،
[دليل relay](closure-webrtc-relay-diagnostic.json)،
[PCM الخام وRTC stats](closure-webrtc-pcm-diagnostic.json).

أثبت `Room.getRtcStats()` وجود `ICE_TRANSPORT_CONNECTED` و
`DTLS_TRANSPORT_CONNECTED` ومرشح بعيد `127.0.0.1:17882` وزوج مرشحين مختار وحزم
وbytes متزايدة. بذلك دُحضت فرضية أن SDK يستبعد loopback بحيث يمنع النقل تمامًا.
لا يُستنتج فشل ICE من نجاح connect/publish وحده؛ هنا الدليل يشمل النقل المفكوك نفسه.

المقارنة أدناه تستخدم **نفس العينات الخام** للمقدرين، وليس نافذتين مختلفتين:

[إعادة الحساب وبصمة ملف العينات](closure-webrtc-oracle-analysis.json).
أكد المراجع المستقل FFT بواسطة numpy، وكانت طاقة نطاق ±25Hz نحو 95.6–98.7%.
الأرقام القديمة داخل snapshot قد تختلف قليلًا عن إعادة الحساب على PCM الملتقط
بعدها ببضعة ms؛ الجدول أعلاه يعيد المقدرين على النافذة الخام الواحدة نفسها.
لا توجد عينات خام للمحاولة التاريخية، لذلك لا ندّعي تشخيص كل حدث فيها بأثر رجعي؛
أُعيد إنتاج عيب oracle بنفس إعداد العزل، وأُغلق بفحص نقل جديد يشمل كل المعايير.

## الإصلاح المحدود والتحقق السلبي

أضيفت أداة اختبار مستقلة `webrtc-audio-metric.mjs` تعتمد FFT radix-2 مع نافذة Hann.
بقيت شروط frames≥15 وRMS>300 و±25Hz كما هي؛ أضيف شرط أن تبلغ طاقة نطاق الإشارة
المتوقعة 80% على الأقل. هذا لا يوسع النطاق لتجاوز فشل. بقي تقدير عبور الصفر في
الدليل باسم `zeroCrossingHz`، بينما أصبح `frequencyHz` تقدير FFT.

**5/5 اختبارات oracle ناجحة، صفر فشل أو تجاوز**:

- تقبل الإشارتين المعروفتين 440/660Hz وترفض إشارة الهوية الأخرى.
- ترفض الصمت وتردد 880Hz والضجيج واسع النطاق.
- ترفض السعة المنخفضة و14 إطارًا فقط.
- تعيد رفض عبور الصفر الخاطئ على التسجيل الخام، ثم قبول التردد الغالب الصحيح.

```sh
node --test tests/voice-acceptance/webrtc-audio-metric.test.mjs
```

لا حزمة جديدة ولا تعديل SDK أو signaling أو media transport. أضيفت actions
تشخيصية لمرشحي ICE وPCM وFD؛ و`--expose-gc` اختياري لتحليل SDK فقط، لا للجولة
الافتراضية. تغير اسم معيار baseline ليصف عدادات الوسائط المرصودة تحديدًا، ولا
يدّعي عودة كل FD/heap إلى خط الأساس.

## نتيجة الجولة المعزولة الجديدة

```sh
/tmp/tahaddi-closure-webrtc/livekit-server --config /tmp/tahaddi-closure-webrtc/livekit.yaml
node tests/voice-acceptance/webrtc-orchestrator.mjs /tmp/tahaddi-closure-webrtc/runtime.json docs/visual-evidence/live-room-responsive/closure-webrtc-verification.json
```

التشغيل: 03:55:21.800–03:55:31.209 UTC، exit 0، **11/11 معيارًا** ضمن سيناريو واحد.
[النتيجة الكاملة](closure-webrtc-verification.json)،
[إعداد العزل دون مفاتيح وبصمات الملفات](closure-webrtc-environment.json).

- عميلان native مستقلان، خادم LiveKit 1.13.10 مثبت بالبصمة، إشارة PCM مولدة فقط.
- A فك إشارة B: FFT=662.11Hz وRMS=4719.21 وتركيز 98.01%؛ المقدّر القديم في
  النافذة نفسها أعطى 732.95Hz، أي كان سيرفض PCM الصحيح.
- B فك إشارة A: FFT=432.13Hz وRMS=4931.27 وتركيز 89.50%؛ كلا الطرفين اجتازا
  شرط ±25Hz الأصلي وشرط التركيز الإضافي.
- ICE وDTLS متصلان؛ bytes المرسلة/المستلمة 15010/9326 لدى A و10768/12080 لدى B
  عند snapshot، مع selected candidate pairs محفوظة في JSON.
- نجح وقف المصدر المولد واستئنافه، وقطع WebSocket فعلي ثم تعافي النقل، وثلاث
  دورات مغادرة/عودة مع عودة عدد المشاركين 2→1→2، دون إعادة حالة الاختبار الفاشلة.
- توقف المصدر المحلي في الدورات خلال 11.03 و7.82 و7.39ms، وRMS البعيد صفر بعد
  سماح التصريف 250ms. هذا لا يثبت زمن توقف ميكروفون مادي أو غياب ذيل مسموع عليه.
- عادت listeners/streams/jobs/source timers المرصودة للصفر، ثم SFU participants
  وrelay connections للصفر، وحُذفت الغرفة. خرج العميلان طبيعيًا code 0/signal null.

خادم الإشارة استمع على 127.0.0.1:17880 وRTC UDP على 127.0.0.1:17882 فقط؛ TCP
fallback معطل. بقي هذا الإعداد نفسه قبل إصلاح oracle وبعده. يحتوي الملف البيئي
على الإعداد غير السري والبصمات وفحص المستمعين، ولا يحتوي مفاتيح API أو JWT.

## الموارد وحدود الاعتماد

حُررت جميع موارد clients وrelay بعد الجولة. أُبقي SFU الخاص مؤقتًا بتنسيق المنسق
لجولة SDK والاستقرار المشتركة، ثم أُوقف بـSIGTERM وexit 0 بعد انتهائها. حُذفت
ملفات runtime المعروفة المملوكة للتشغيل ومفاتيحه وسجلاته وملفه التنفيذي المؤقت،
بعد التحقق من الملكية وعدم وجود symlinks؛ المنافذ الأربعة خالية. لم تُحذف صورة
Docker أو SDK المشترك. [دليل التنظيف](closure-webrtc-cleanup.json).
سجل Pion ثلاثة مرشحين متأخرين ذوي ufrag غير مطابق أثناء إعادة اتصال الاستقرار؛
حُفظ ملخصهم في دليل التنظيف بدل إخفائه. نجحت معايير التعافي الثلاثة، وهذه الرسالة
وحدها لا تثبت خللًا في صوت التطبيق.
لا مساس بملفات SDK المثبتة أو تعديلات المستخدم أو قاعدة بيانات التطبيق.

أُغلقت فجوة فشل أداة قبول PCM المعزول بالدليل الحالي. تبقى مستقلة: تحليل native
FDs طويل العمر، ومسار browser AudioSession وبوابة admission والإبطال الفعلية،
وشبكات NAT/TURN وقطع ICE، وصوت الجهازين ولوحة مفاتيح الجوال الفعليان. لا تُنسب
هذه النتائج إلى أجهزة حقيقية، ولا تمنح وحدها جاهزية إنتاج. لا Push أو نشر.
