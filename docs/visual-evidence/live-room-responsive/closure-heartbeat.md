# إغلاق طلبات heartbeat بعد المغادرة

التاريخ: 21 أكتوبر 2026. المراجع المستقل: `close_heartbeat`.
المرجع السابق: [approval-final.md](approval-final.md).

**ثبت عيب تنظيف في التطبيق وأُصلح ضمن `VoiceRoomView`:** كانت قراءة heartbeat
الجارية تبقى إلى مهلة 10 ثوانٍ بعد unmount، ولم تكن المغادرة نفسها توقف مالك polling.
أصبح الطلب الجاري ومؤقته يُلغيان عند المغادرة أو انتهاء المكوّن أو تبديل الغرفة،
مع منع استجابة قديمة أو إعادة polling من المالك المتوقف.

## السبب المثبت قبل التعديل

- effect الخاص بـheartbeat امتلك `stopped` ومؤقت polling فقط، ولم يمرر owner
  `AbortSignal` إلى `voiceRequest`. كان cleanup يمنع تطبيق الرد وإعادة polling
  بعد unmount، لكنه لا يلغي `fetch` أو مؤقت مهلة القراءة الجاري.
- `leave()` أوقف الوسائط المحلية، دون إيقاف heartbeat. إذا تأخر إقرار المغادرة
  أو فشل وبقي المكوّن mounted، أمكن استمرار قراءات polling؛ ليس الحد دائمًا طلبًا
  واحدًا يبقى 10 ثوانٍ فقط.
- قراءة `refreshRoom` المؤجلة التي يطلبها حدث وسائط كانت أيضًا بلا owner signal.
  cleanup للمؤقت وحده لا يكفي إذا بدأ HTTP بالفعل.

أخفق [الاختبار الأول قبل الإصلاح](closure-heartbeat-before.json) في ست حالات عند
`signal.aborted === false` بدل `true`، دون خطأ إعداد أو مهلة اختبار.
أثبت [اختبار refresh المستقل](closure-heartbeat-refresh-before.json) الذيل نفسه.
كذلك كشف [اختبار سباق تبديل الغرفة](closure-heartbeat-refresh-race-before.json)
أثناء تطوير الإصلاح أن finally قديمًا قد يجدول تحديثًا للغرفة `one` بدل `two`؛
أُغلق ذلك بحراسة جيل المالك وهويته قبل apply أو تعديل refs أو إعادة الجدولة.

## الإصلاح المحدود

التعديل الإنتاجي محصور في
[`voice-room.tsx`](../../../apps/web/src/components/voice/voice-room.tsx):

- `AbortController` لكل مالك heartbeat، مشترك بين قراءة events وقراءة fallback
  بعد رفض العضوية؛ cleanup idempotent يوقف المؤقت ويلغي الطلب ويُسقط المالك.
- استدعاء cleanup تزامنيًا عند بدء `leave()`، قبل انتظار كتابة المغادرة؛ لا يمر
  `AbortSignal` الخاص بالقراءة إلى طلب `/leave`.
- مالك مستقل لقراءة `refreshRoom` مع إلغاء HTTP والمؤقت عند leave/unmount/room change،
  وgeneration/identity guards تمنع finally أو رد مالك قديم من التحكم بمالك جديد.
- إلغاء مقصود لا يعرض رسالة شبكة زائفة، ولا يعيد polling. بعد رفض المغادرة يبقى
  خطأ الخادم وزر إعادة المحاولة الصريحة متاحين؛ تظل الوسائط محليًا متوقفة كما كانت
  سياسة التطبيق قبل الإصلاح. تبديل roomId ينشئ مالك polling جديدًا.

لم يتغير نقل الوسائط أو `AudioSession` أو تنسيق الواجهة أو مهلة 45 ثانية.
إلغاء fetch في المتصفح **لا يضمن إلغاء عملية أو معاملة بدأت على الخادم**.
لم نعمم الإصلاح على جميع طلبات الفتح والكتابة والملف الشخصي؛ النطاق هو قراءات
heartbeat وrefresh المرتبطة بمالك الغرفة.

## التحقق الفعلي

شُغلت المجموعة بعامل واحد بعد إذن المنسق بنافذة الموارد، مع HTTP وAudioSession
محاكيين، و`VoiceRoomView` و`voiceRequest` الفعليين. لم يُشغّل SFU لهذا الاختبار.
الساعة افتراضية لا تعطي p95 لزمن شبكة حقيقية.

| الحالة | النتيجة النهائية |
| --- | --- |
| قراءة جارية وقت leave المعلق | تُلغى تزامنيًا؛ write يبقى حيًا عند 10,000 و44,999ms ويُلغى عند 45,000ms |
| leave مرفوض ثم إعادة صريحة | القراءة ملغاة، خطأ الخادم محفوظ، لا polling خلال 60s افتراضية، والمحاولة الثانية تنجح |
| unmount | قراءة ملغاة، وصفر مؤقتات بعد microtasks/cleanup دون انتظار 10s |
| تبديل roomId ورد HTTP متأخر | المالك القديم ملغى، لا تطبيق للرد القديم، والمالك الجديد يواصل polling |
| StrictMode | المالك الحي يستمر بعد replay ويُلغى عند final teardown |
| رفض العضوية 403 وfallback | قراءة fallback تُلغى مع cleanup؛ خطأ الصلاحية يبقى ظاهرًا |
| refresh بدأ قبل المغادرة | طلبه ومؤقته يُلغيان، دون ذيل 10s |
| abort قديم ثم refresh جديد قبل تسوية rejection | لا إعادة جدولة للغرفة القديمة ولا مساس بمالك الغرفة الجديدة |

**النتيجة النهائية: 8 ناجحة، صفر فشل أو تجاوز، خلال 4.98s، exit 0.**

## أثر قرار الاعتماد

أُغلق ذيل القراءة المحلي المحدد ودورات إعادة polling غير المرغوبة في الحالات
المختبرة. لا تثبت هذه المجموعة إلغاء العمل الخلفي للخادم، أو الصوت على أجهزة
فعلية، أو سلامة SFU أو SDK الأصلي؛ لها أدلة مستقلة. المخاطر العامة وقرار الاعتماد
تُدمج في مراجعة المنسق دون استنتاج جاهزية الإنتاج من هذه المجموعة وحدها.
