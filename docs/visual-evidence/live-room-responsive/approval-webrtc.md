# اعتماد نقل WebRTC المحلي بين عميلين مستقلين

هذا تحقق من نقل الوسائط باستخدام SFU فعلي وعمليتي Node مستقلتين، مع PCM مولّد
بترددَي 440 و660Hz. لا يثبت جودة ميكروفون أو سماعة أو هاتف فعلي، ولا يغطي
تسجيل الدخول أو عضوية الغرفة ومسار admission في التطبيق.

## البيئة وطريقة إعادة التشغيل

- LiveKit Server 1.13.10، صورة رسمية مثبتة عند
  `livekit/livekit-server@sha256:89ca9ce0791e18d6e03bf6e2c49ceb27e1c754eae8bd50c989386c1a5963791a`.
- SHA256 للملف التنفيذي المستخرج:
  `5153d7ce95fb2f2ffb455a0e4ac464be2c94a38c77c99fd728f9c61748a11381`.
- `@livekit/rtc-node` 1.1.0 مع native bindings 0.12.73؛ كل عميل عملية مستقلة.
- إعداد إعادة الإنتاج الحالي يربط signaling على `127.0.0.1:17880` وUDP على
  `127.0.0.1:17882` فقط؛ TCP fallback معطّل (`tcp_port: 0`) ويبقى 17881 غير
  مستخدم. relay الإشارة المحلي على 17890 يتيح قطع WebSocket فعلي دون تغيير
  firewall أو شبكة المضيف. هذا الإعداد هو محاولة العزل الثانية الفاشلة في PCM،
  وليس إعداد الجولة الأولى الناجحة.
- مفاتيح تطوير مولّدة لكل جلسة، محفوظة خارج المستودع في ملفات mode 600؛ لا
  مفاتيح إنتاج أو أسرار تطبيق مستخدمة. لا push أو نشر.

```bash
node tests/voice-acceptance/webrtc-local-setup.mjs /tmp/tahaddi-approval-webrtc
/tmp/tahaddi-approval-webrtc/livekit-server --config /tmp/tahaddi-approval-webrtc/livekit.yaml
# في نافذة موارد حصرية، بعد استماع الخادم:
node tests/voice-acceptance/webrtc-orchestrator.mjs /tmp/tahaddi-approval-webrtc/runtime.json docs/visual-evidence/live-room-responsive/approval-webrtc-result.json
```

التحضير يرفض الكتابة فوق جلسة قائمة. يُوقف الخادم بعد الاختبار وتُزال ملفات
المفاتيح المؤقتة عند انتهاء الحاجة. سجلات native الخاصة تبقى خارج المستودع.

## القياسات المطلوبة

1. فك PCM في الاتجاهين، مع RMS وتقدير التردد.
2. إيقاف المصدر المولّد واستئنافه؛ هذا ليس اختبار زر كتم المتصفح.
3. استعادة SDK بعد قطع WebSocket حقيقي عبر relay؛ تختلف هذه عن المغادرة ثم
   الاتصال في جلسة جديدة.
4. ثلاث دورات مغادرة ثم عودة للعميل A، مع بقاء B متصلًا وعودة عدد المشاركين
   في الخادم من 2 إلى 1 ثم 2 في كل دورة.
5. وقت إيقاف توليد الإطارات المحلي، ثم طاقة PCM لدى الطرف الآخر بعد سماح
   250ms لتصريف jitter/decoder. هذا حد قياس للاختبار، ولا يعني غياب ذيل صوت
   مسموع على جهاز فعلي.
6. تعداد listeners وstreams وconsumer jobs والمؤقت والمصدر بعد المغادرة؛
   ثم صفر مشاركين واتصالات relay وخروج العمليتين طبيعيًا بعد dispose.

هذه ليست 11 وحدة اختبار منفصلة. لا تُجمع الجولة الناجحة مع الفاشلة لإعلان
اعتماد كامل، ولم تُرفع المهلة أو تُضعف شروط PCM لتجاوز الفشل.

الجولة الأولى استخدمت `bind_addresses: [127.0.0.1]`، لكن فحص `ss` كشف أن هذا
الحقل قيّد signaling فقط: UDP استمع أيضًا على واجهات المضيف وTCP على wildcard.
كل الاتصالات المقصودة كانت محلية، لكن **الجولة الأولى ليست loopback-only**.
أُوقفت بعد حفظ نجاح النقل، ثم صُحّح إعداد الاختبار فقط باستخدام حقول الإصدار
الرسمية `rtc.interfaces.includes: [lo]` و`rtc.ips.includes: [127.0.0.1/32]`، مع
تعطيل TCP fallback ذي مستمع wildcard. أُعيد السيناريو مرة واحدة بسبب هذا
التعديل، بعد إثبات `ss` لاستماع 127.0.0.1 فقط.

السبب الجذري لفشل PCM في الجولة الثانية **غير مثبت**: connect/publish نجحا
بـ 184.87 و163.49ms مع publication واحدة لكل عميل، لكن لم تُحفظ سجلات ICE
تفصيلية أو candidate-pair stats في هذه الجولة. استبعاد loopback في ICE داخل
المكتبة الأصلية احتمال يحتاج إثباتًا؛ لا يُنسب الفشل إلى منطق صوت التطبيق.
لم تُشغّل محاولة ثالثة. التحقق التالي المناسب يبدأ بتسجيل candidates وselected
pair من `Room.getRtcStats()` في probe محدود، قبل اقتراح عزل شبكي بديل أو إعادة
سيناريو كامل. يبقى نجاح الجولة الأولى دليل نقل محدودًا واضح الحدود.

### مقاييس الجولة الأولى الناجحة

- فك A لتردد B المولّد: 45 إطارًا، RMS=6835.67 وتقدير 672.22Hz؛ فك B لتردد A:
  45 إطارًا، RMS=6820.57 وتقدير 445.56Hz. التقدير يعتمد عبور الصفر وليس محللًا
  طيفيًا دقيقًا؛ التوقع بقي ±25Hz حول التردد المولّد.
- إيقاف المصدر المولّد أنتج RMS=0 لدى B بعد سماح التصريف 250ms، ثم عاد PCM
  عند الاستئناف. هذا يختبر مصدر الاختبار، لا زر كتم الميكروفون في التطبيق.
- قُطع WebSocket حقيقي واحد للعميل A. رُصد `reconnecting` ثم `reconnected`
  بعد 1052ms من القطع؛ اكتمال فحص عودة PCM ثنائي الاتجاه استغرق 5118ms.
  لم يُقطع مسار ICE نفسه ولم تُختبر خسارة شبكة حقيقية أو TURN.

توقف توليد الإطارات المحلي قبل disconnect في كل دورة. آخر إطار ذي طاقة عند
الطرف الآخر وصل في الدورة الأولى بعد توقف المصدر بـ 10ms، وفي الثانية بـ 6ms،
وفي الثالثة كان قبل توقفه بـ 51ms. لذلك لا تُفسّر مهلة تصريف 250ms على أنها
زمن استمرار التقاط محلي، ولا على أنها ضمان صمت سمعي على الأجهزة الحقيقية.

عاد عدد المشاركين بالخادم 2→1→2 في الدورات الثلاث. بعد كل مغادرة أصبحت عدادات
room listeners وFFI listeners وstreams وconsumer jobs صفرًا؛ أُغلق المصدر وتوقف
مؤقته. اسم معيار JSON `threeChurnCyclesReturnToNativeBaseline` يخص **هذه العدادات
المرصودة فقط**: لم تعد FDs إلى baseline، ولا يثبت الاختبار غياب تسرب native
FD/heap. تذبذب FDs لا يكفي وحده لإثبات تسرب تراكمي أو نفيه؛ يلزم قياس native
أطول مع فترة استقرار وتفسير الموارد المشتركة إذا أريد إغلاق هذا الخطر.

### التنظيف

في الجولة الأولى عاد عدد المشاركين وrelay connections إلى صفر، وحُذفت الغرفة،
وخرج العميلان طبيعيًا بعد dispose بـ code 0 وsignal null دون forced kill.
في الثانية نفّذ مسار التنظيف إغلاق العميلين وحذف الغرفة، ولم يُسجّل
`forcedChildExit`؛ لم تُحفظ exit codes الفردية في JSON الفشل، فلا تُنسب لهما
نفس دقة دليل الخروج الطبيعي في الأولى. لا توجد عمليات عميلين باقية.

أُوقف SFU في المحاولتين بـ SIGTERM مع خروج shell code 0. فحص `ss` النهائي أثبت
خلو 17880/17881/17882/17890. حُذفت ملفات `runtime.json` و`livekit.yaml` التي تحمل
المفاتيح المؤقتة فقط، مع الاحتفاظ بالـ metadata/checksums والسكريبتات والصورة
المخزنة. لا موارد إنتاج مستخدمة ولا أسرار محفوظة ضمن أدلة المستودع.

## حدود الاعتماد

- الصوت بين جهازين وميكروفونين فعليين: **غير منفذ**؛ لا أجهزة مادية متاحة.
- NAT وTURN والإنترنت وشبكات الجوال وقطع مسار ICE: **غير منفذة** في هذا النطاق.
- اختبارات القبول في التطبيق وإبطال العضوية/الرمز بعد المغادرة: **غير مغطاة**
  بهذا SFU الخام؛ يلزم مسار admission الفعلي.
- عدادات الموارد والخروج الطبيعي دليل محدود على تنظيف الموارد الملحوظة؛
  ليست برهانًا شاملًا على غياب تسرب heap أو native memory طويل الأمد.
- الجولة المعزولة فاشلة حاليًا، وعودة FDs إلى baseline غير مثبتة. لا يُعلن هذا
  التقرير جاهزية إنتاج أو يغلق مخاطر نقل المتصفح/الأجهزة الفعلية.
- لم يتغير منطق صوت التطبيق أو مهلة المغادرة 45 ثانية أو إصلاح المقاعد عند
  تكبير النص إلى 200%.
