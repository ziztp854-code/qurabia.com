# SDK: سلامة الملفات وتفسير واصفات الملفات

المراجع المستقل: `close_sdk`، 21 أكتوبر 2026. المرجع السابق: [مخاطر القبول](approval-final.md).

## سلامة النسخة الأصلية

جرى حساب SHA512 فعليًا لكل ملف منشور في الحزم الثلاث المثبتة، ومقارنته بفهرس
مخزن pnpm الأصلي. طابقت مفاتيح SRI لذلك الفهرس قيم `pnpm-lock.yaml`:

| الحزمة | الإصدار | الملفات المفحوصة | اختلافات |
| --- | --- | ---: | ---: |
| `@livekit/rtc-node` | 1.1.0 | 189 | 0 |
| `@livekit/rtc-ffi-bindings` | 0.12.73 | 32 | 0 |
| `@livekit/rtc-ffi-bindings-linux-x64-gnu` | 0.12.73 | 3 | 0 |

**224/224 ملفًا مطابقًا**، بما فيها الشيفرة التنفيذية وملف native. لا ملف patch
إضافي داخل الحزم؛ يوجد shims اثنان يولدهما pnpm لـ`pino` و`pino-pretty`.
فحص `git diff -- package.json pnpm-lock.yaml` فارغ. هذا تحقق جديد من الملفات،
وليس نتيجة اختبار معادة من cache. مصدر المقارنة هو فهرس التثبيت المحلي المرتبط
بالـlock؛ لم يُنزّل tarball جديد ولم يُغيّر المخزن أو SDK.

الحالة المثبتة أصلية بالفعل؛ لم تحتج استعادة أو إعادة تثبيت، ولم يُكتب فوق أي
تعديل مستخدم. [البصمات المتوقعة والفعلية لجميع الملفات](closure-sdk-integrity.json).

الحزمة native موجودة ضمن devDependencies الجذرية. لم يُعثر على استيراد
`@livekit/rtc-node` في شيفرة `apps` أو `packages` الإنتاجية؛ تستخدمها أدوات الاختبار.
لا يجوز نسبة خصائص مواردها مباشرة إلى `livekit-client` في متصفح التطبيق.

## المقارنة الباردة لا تثبت التسرب

أُجري probe مستقل دون خادم أو شبكة، باستخدام ثلاث دورات إنشاء/التقاط/إغلاق
AudioSource، ثم استقرار 1s وGC تشخيصي وإغلاق FFI:

| المرحلة | FD مستقرة قابلة لقراءة الرابط |
| --- | ---: |
| بعد import وقبل أول تهيئة native | 27 |
| بعد أول AudioSource وإغلاقه | 35 |
| بعد المصدر الثاني والثالث | 35 |
| بعد الاستقرار ثم GC اختباري | 35 |
| بعد `dispose()` | 35 |

الزيادة الثابتة **8**: أربعة `eventpoll` واثنان `eventfd` واثنان Unix sockets،
دون TCP/UDP. ظهرت مع التهيئة الأولى، ولم تتكرر مع دورات المصادر. تتسق مع موارد
runtime مشتركة طويلة العمر؛ لا يصح عدها تسرب جلسة بالرجوع إلى baseline بارد.
لا نستنتج من بقائها بعد `dispose` إغلاق كل موارد العملية؛ خرج probe طبيعيًا برمز 0.
[الأنواع والروابط وsocket inodes والعينات](closure-sdk-runtime.json).

```sh
node --expose-gc tests/voice-acceptance/sdk-fd-runtime-probe.mjs docs/visual-evidence/live-room-responsive/closure-sdk-runtime.json
```

تتحقق assertions من ثبات الأنواع والعدد بعد warmup عبر الدورات والإغلاق.
GC تشخيص للاختبار فقط، وليس متطلبًا مضافًا إلى المنتج. أُعيد probe القصير مرة
بعد إضافة هذه assertions؛ لم يُعد حمل SFU بسبب هذا التحقيق المحلي.

الأرقام القديمة 29/106/52/97 مأخوذة من `readdir('/proc/self/fd')`؛ عند قراءة
`self/fd` قد تُحسب مؤقتًا خانة دليل القراءة نفسه. helper الجديد يعرض
`listedEntries` و`stableCount`، ويتجاهل الروابط التي اختفت وقت القياس. كما يربط
socket inodes بـ`/proc/<pid>/net` لتفريق sockets الوسائط عن موارد runtime.
اختلاف stdio/IPC بين probe والعميل القديم يمنع مقارنة 27 مباشرة بـ29.

## موارد جلسات الغرفة

من قراءة SDK الأصلي: `Room.disconnect()` ينهي الاتصال ويزيل المستمعين، لكنه
لا يتخلص صراحةً من `ffiHandle` الخاص بالغرفة في ذلك الموضع. أداة الاختبار القديمة
تحتفظ كذلك بـ`lastRoom` بعد المغادرة لأغراض التشخيص. أثر الاحتفاظ بالمراجع وGC
لا يثبت وحده سبب FD. كذلك `LocalAudioTrack.close(closeSource=true)` يغلق المصدر
افتراضيًا، فلا يوجد دليل أن فرع `track.close()` نسي إغلاقه.

أُدرج helper في [جولة الاستقرار الواحدة](closure-stability-result.json)، دون
تشغيل soak ثانٍ لهذا التحقيق. نفذت 12 دورة و3 استردادات WebSocket حقيقية:

| المرحلة بعد مغادرة العميلين | A | B | واصفات UDP في A |
| --- | ---: | ---: | --- |
| استقرار طبيعي 5s، والمراجع التشخيصية باقية | 58 | 39 | 19، جميعها DNS |
| إسقاط `lastRoom` ثم مرور 2s، دون GC | 43 | 39 | 4، جميعها DNS |
| GC تشخيصي واحد ثم 2s | 43 | 39 | 4، جميعها DNS |

**سبب فرق FD المتبقي أصبح مصنفًا بالأدلة:** الموارد غير UDP متطابقة بين العميلين
وتساوي baseline دافئًا قدره 39، والزيادة فوقه sockets متصلة بمحلل DNS المهيأ
للبيئة. كل UDP في العينة الطبيعية الأولى، وكذلك الأربعة الأخيرة، تتجه إلى
`172.31.1.29:53`، وهو nameserver الفعلي في `/etc/resolv.conf`.
لا UDP أو TCP متبقٍ إلى SFU أو منفذ الوسائط في هذه العينات؛ لم تكن تلك الأربعة
مسارات إرسال أو التقاط صوت باقية. [الـinodes والعناوين المفكوكة والأنواع](closure-sdk-socket-analysis.json).

الـinodes الأربعة الأخيرة: `188013`, `190528`, `188973`, `188975`، مع منافذ
DNS محلية 35412 و58008 و51746 و35149. هذه أرقام داخل بيئة الاختبار، وليست
ملفات مستخدم معدلة أو إعدادات إنتاج. انخفضت المقابس الخلفية 19→4 مع
مرور الوقت؛ لا يثبت ذلك أن إسقاط المرجع نفسه سبب الانخفاض، لأن العاملين تزامنا.

لم تُلتقط أسماء استعلامات DNS أو شيفرة resolver/timeout الأصلية في تلك الجولة؛
**لا نثبت حدًا زمنيًا أقصى لبقاء DNS ولا ننفي كل تسرب native طويل الأمد**.
لم يتسبب GC في تحرير الأربعة خلال القياس. يتطلب سؤال عمر DNS تشخيصًا متخصصًا
إن كان اعتماد harness native طويل العمر مطلوبًا؛ لا يستدعي دليلنا تعديل صوت
المتصفح أو patch SDK. انتهت العمليتان طبيعيًا برمز 0، ولم تَبقَ واصفات لهما بعد الخروج.

أُغلقت شبهة أن الأعداد الخام تثبت بقاء اتصال وسائط أو فساد SDK. يبقى حد DNS
الخلفي موثقًا، ولا تتحول هذه المجموعة إلى شهادة خلو مطلقة من التسرب أو اعتماد إنتاجي.

## الأسرار والملفات المؤقتة

[الجرد المحدود للأسرار والملفات](closure-sdk-cleanup.json) يفحص مجلد runtime
السابق المملوك للاختبار فقط. ملفا المفاتيح `runtime.json` و`livekit.yaml` غائبان،
ولا JWT مطابق للنمط في سجلاته. الفحص لا يقرأ محتوى descriptors ولا يطبع أسرارًا.
بعد تأكيد الوكيل الأول عدم استخدام المجلد القديم، طوبقت قائمة ملفاته التسعة
وملكيتها ونوعها وعدد الروابط وبصمة ملف LiveKit المثبت، وتحقق عدم وجود FD أو
executable مفتوح عليها. حُذفت الملفات التسعة والدليلان الفارغان بمسارات محددة؛
مجلد `/tmp/tahaddi-approval-webrtc` القديم غائب الآن. لم تتغير صورة Docker المخزنة
أو runtime الجولة الحالية المملوك للوكيل الأول.
حُذفت ملفات تحليل مخزن pnpm المؤقتة الخاصة بهذه المهمة بعد حفظ البصمات؛ بقيت
أدوات الاختبار والأدلة المقصودة في المستودع، دون تعديل SDK أو بيانات التطبيق.

لم يتغير منطق الصوت أو مهلة المغادرة 45 ثانية أو CSS. لا Push أو نشر.
