# فحص أداء كتابة دردشة البث

## النطاق والبيئة

شغّل هذا الفحص Chromium 151 على Linux في بيئة سحابية، بمعالج Xeon Platinum 8573C وحصة CPU قدرها أربع نوى، وviewport ‏1440×900 وDPR=1. استُخدمت شجرة `VoiceRoomView` الفعلية وCSS الفعلي، وستة مشاركين و200 رسالة، منها رسائل صاحب شارة المالك. النقل HTTP و`AudioSession` محاكيان محليًا؛ لم يحدث التقاط ميكروفون أو اتصال SFU في هذا القياس. هذه ليست أجهزة جوال حقيقية أو قياس Safari أو Android.

البناء Vite/React development، مع React Profiler ومجسات تصيير في fixture فقط، ودون StrictMode. التطوير وأدوات القياس يزيدان الكلفة؛ لا تُنقل الأرقام مباشرة إلى الإنتاج. لا توجد مجسات قياس في ملفات المنتج. مُنع تشغيل QA أو اختبارات ثقيلة بالتزامن مع نوافذ القياس.

الزمن المسجل هو من التقاط حدث `input` إلى أول callback تالٍ لـ`requestAnimationFrame` بعد معالجة React. إنه **مؤشر لفرصة تحديث الإطار**، وليس توقيت ظهور البكسل على الشاشة أو INP، ولا يشمل انتظار الحدث قبل دخوله الخيط الرئيسي. قِيس أيضًا React `actualDuration` وLong Tasks وCDP `TaskDuration`/`ScriptDuration`؛ الأخيرتان ثوانٍ تراكمية من عمل الخيط الرئيسي، وليستا نسبة CPU للنظام.

## السبب المثبت

حالة النص كانت محلية أصلًا داخل `VoiceChat`؛ لم تكن تنتظر Socket أو API، ولم يكن كل حرف يعيد تصيير `VoiceRoomView`. لكنها كانت تشارك المكوّن نفسه مع سجل الرسائل: كل حرف يعيد بناء صفوف السجل و`Avatar` و`MemberName` والخرائط والوقت المحلي لكل رسالة. مع 100 حرف و200 رسالة، سجلت العينة الأصلية 20,400 تقييم JSX لصفوف الرسائل و102 تصيير لـ`VoiceChat`، مقابل تصيير واحد للغرفة من تحديث خلفي.

عزل Composer وحده خفّض p95 إلى 18ms في العينة الأولى بعد التعديل، لكنه كشف سببًا ثانيًا مثبتًا: تحديث المتحدث/heartbeat ما زال يعيد تصيير السجل. مع عشرة تغييرات متحدث، ظهرت 3,000 إعادة تقييم لصفوف الرسائل و26 Long Task وp95=235.2ms. لذلك كان التعديل الثاني المبرر هو عزل الصفوف بـmemo مع مقارنة بيانات الرسالة كاملة وبيانات العرض الفعلية لصاحبها واستقرار handlers، دون تغيير منطق النقل أو الصوت.

## القياسات الفعلية

كل عينة تكتب 100 حرف بالمتصفح و200 رسالة. p95 هو nearest-rank، والأزمنة بالـms إلا عمودَي CDP بالثواني.

الأعداد تخص المكونات المراقبة، ولا تزعم عدّ كل مكوّن أيقونة داخل شجرة React. تصيير الصفوف النهائي صفر أثناء النافذتين، مع 200 تصيير مبدئي مثبت في `probeTotals`. تصيير الغرفة خلفي: قراءة heartbeat واحدة في الكتابة، وعشرة تغييرات متحدث وقراءة heartbeat في السيناريو الثاني. لا يسبب حرف الإدخال تلك التحديثات.

نجح القياس النهائي 2/2 خلال 23.1 ثانية، واحتُفظ بكل الأحرف والتركيز والمؤشر عند 100. لم يُرسل أي POST أثناء نافذة الكتابة؛ طلب API الوحيد في كل نافذة GET heartbeat. ظل مصدر chat نفسه SHA-256 `6aaed1f3f23b3e928a3a5273c770c5703c0f976b00d4a9ddf9e6e64a7cb4fd5c` في النافذتين، ولم يتغير مصدر الغرفة.

تحقق الهدف المرصود p95 أقل من 50ms في النافذتين. تبقى استثناءات موثقة: أقصى مؤشر إطار مع المتحدث 147ms و13 Long Task، أطولها 344ms؛ لذلك لا ندّعي أن كل ضغطة أقل من 50ms أو اختفاء جميع مهام الخيط الرئيسي. زمن callback لا يكشف انتظار لوحة المفاتيح قبل حدث input، والاختبار لا يثبت سلاسة كل جهاز أو بث حقيقي. لا تبرر هذه النتيجة تغيير منطق الصوت أو تعطيل الشارات، ولا تتطلب إعادة قياس مماثل بلا معلومة جديدة.

## سلامة القياس

- `before-isolated.json`: اكتمل قياس 100 حرف وحُفظ النص والمؤشر والتركيز. كانت قراءة heartbeat معلقة في route الاختبار؛ انتهت مهلة القراءة الأصلية 10 ثوانٍ أثناء العينة، فأضافت تحديث غرفة واثنين من commits الدردشة. ثم فشل teardown في fixture بخطأ `apiResponse.json: Response has been disposed` بعد تحرير الطلب. هذا خطأ تجهيز الاختبار، وليس فشل منتج؛ أبقينا الملف الخام ولم ندّع نجاح هذا التشغيل. الأرقام 102 commits و20,400 صف تشمل التحديث الخلفي، وليست 102 حرفًا.
- `before-speaking.json`: نجح التشغيل 1/1، بعشرة تغييرات متحدث محددة. كانت هذه العينة قد حمّلت transform مؤقتًا يؤخر بدء polling في fixture فقط؛ حُذف من الملفات المحتفظ بها. لا نعرض فروق أزمنتها كنسبة تحسن مضبوطة أمام العينات التي تعمل بـheartbeat الطبيعي.
- `composer-only-*.json`: تشغيل فعلي ناجح 2/2 بعد استخراج Composer؛ يحتفظ بالدليل على الحاجة إلى إصلاح تحديثات الخلفية. heartbeat طبيعي، بلا تغيير للمهلة.
- `after-*.json`: القياس النهائي على المصدر المدمج. heartbeat طبيعي، ولا gate أو تغيير مؤقت للمهلة. يتضمن مصدرَي chat/room بـSHA-256 وأحداث API التي حدثت داخل نافذة القياس.
- قبل الاستخراج، `MessageRow` يعد تقييم JSX المضمن. بعد الاستخراج، `ChatMessageRow` يعد دخول دالة الصف الفعلية بعد اجتياز memo، ولا يعد map أو wrapper. `probeTotals` يثبت أن مجسات الصفوف اشتغلت عند التحميل، حتى حين تكون إعادة تصييرها أثناء الكتابة صفرًا.

الاختلافات الخلفية موثقة؛ المقارنة الأساسية الموثوقة لإثبات الإصلاح هي إزالة عمل الرسائل من مسار تحديث النص، مدعومة باختبار regression مستقل. قياسات الزمن وصفية لهذه البيئة، ولا تمثل ضمانًا لجميع الأجهزة.

## الحركات والتخطيط

لا تستورد مكونات voice التي فُحصت GSAP؛ حركات المتحدث تستخدم CSS transform/opacity، وwave يوقف animation حتى يصبح المتحدث نشطًا. لا تغييرات على الشارات أو الدخول أو المقعد أو CSS. لم يثبت أن تعطيل هذه المؤثرات مطلوب.

تأثير التمرير التلقائي مرتبط بالرسائل، لا بقيمة النص. قبل الإصلاح، تحديثات الغرفة تعطي props جديدة للدردشة؛ بعد عزل الصفوف تبقى كلفة reconciliation البسيطة والتحديثات الحقيقية، بينما لا يعاد حساب محتوى 200 رسالة لكل حرف. `LayoutCount` يشمل عمل textarea الطبيعي؛ لا يُفسّر كل layout على أنه تخطيط مقاعد. fixture لا يشمل كل مزودي الحركة المحتملين في shell التطبيق الكامل، لذا لا يدّعي قياس GSAP العالمي للإنتاج.
