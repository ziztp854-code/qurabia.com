# اعتماد إصلاح استجابة الكتابة في دردشة البث

أُنجز العمل بأربعة وكلاء مستقلين مع دمج مركزي وملكية ملفات منفصلة، انطلاقًا من `b78162f6a3314d1f9131a2d210220e15221cd036`. أذن المستخدم بالرفع والنشر أثناء التحقق النهائي؛ تُتابع نتيجة الإصدار منفصلة عن نتائج الاختبارات المحلية أدناه.

## السبب الجذري المثبت والإصلاح

كانت حالة المسودة محلية بالفعل داخل `VoiceChat`، ولا تنتظر الشبكة. لكنها كانت مشتركة مع تصيير سجل الدردشة؛ كل حرف يعيد تنفيذ قائمة الرسائل والأفاتار والشارات وتنسيق التواريخ والبحث عن الردود. أثبت React Profiler ومجسات المتصفح واختبار انحدار مستقل هذا العمل. **لم تكن الغرفة الصوتية كلها تعيد التصيير عند كل حرف.**

استخراج `VoiceChatComposer` عزل حالة `text/sending`، لكنه لم يكن كافيًا: قياس النسخة الوسيطة أثبت أن تحديث المتحدث وheartbeat يعيدان تصيير الرسائل بسبب إعادة إنشاء كائنات بيانات العرض. لذلك أُضيف `ChatMessageRow` محفوظ بـmemo، بمقارنة بيانات الرسالة كاملة، وبيانات عرض صاحبها الفعلية، والنص المقتبس، وهوية المستخدم والصلاحيات والـhandlers. تظل تغييرات التفاعلات والتثبيت والنص والصورة والهوية والشارات ظاهرة. لا تُغيّر المقارنة snapshot أو الصلاحيات أو البيانات الصوتية.

التمرير التلقائي يعتمد تغيّر `messages`، ولا يعمل بسبب تعديل المسودة وحده؛ لم نغيّره. مفاتيح الرسائل مستقرة، والتاريخ محدود بـ200 رسالة؛ لا تستدعي هذه المشكلة إدخال virtualization. استُبدل البحث المتكرر عن الرسالة المقتبسة بخريطة محلية.

لم يُضف Debounce أو مؤقت أو مستمع أو Provider، ولم يتغير CSS أو التصميم أو WebRTC/SFU أو مهلة المغادرة البالغة 45 ثانية أو قواعد الإرسال ومكافحة الإغراق. الحقل يحدّث النص مباشرة؛ احتُفظ بسلوك تعطيله أثناء انتظار إقرار إرسال رسالة، وحفظ المسودة عند الفشل ومسحها بعد النجاح.

## قياسات قبل وبعد

Linux سحابي، Xeon Platinum 8573C، حصة أربع نوى، Chromium 151، DPR=1، ستة مشاركين، 200 رسالة وشارة مالك، 100 حرف، viewport ‏1440×900. شجرة الغرفة وCSS فعليان؛ HTTP وAudioSession محاكيان. البناء React development مع Profiler ومجسات اختبارية، دون StrictMode، ودون اختبارات متنافسة أثناء القياس.

| القياس | قبل | بعد الإصلاح النهائي |
| --- | ---: | ---: |
| مؤشر input إلى callback الإطار التالي، p95، كتابة | 525.7ms | 23.9ms |
| أقصى مؤشر إطار، كتابة | 709.7ms | 41.3ms |
| تقييم/تصيير صفوف الرسائل أثناء 100 حرف، كتابة | 20,400 | 0 |
| تصيير VoiceChat أثناء 100 حرف، كتابة | 102 | 1 خلفي |
| تصيير الغرفة أثناء 100 حرف، كتابة | 1 خلفي | 1 خلفي |
| مجموع React actualDuration، كتابة | 16,083.7ms | 204.4ms |
| CDP عمل الخيط الرئيسي، كتابة | 28.153s | 1.643s |
| Long Tasks، كتابة | 116؛ أقصاها 769ms | 1؛ مدتها 66ms |

المسار المحلي لكل حرف أصبح Composer وحده، دون تشغيل صفوف الرسائل. الأعداد للمكونات المراقبة، لا لكل أيقونة في React. قبل الاستخراج كان العداد يقيس JSX المضمن للصفوف؛ بعده يقيس دخول دالة الصف الفعلية، مع إثبات 200 تصيير مبدئي في `probeTotals`، ثم صفر أثناء الكتابة. تشمل العينة الأصلية تحديثين خلفيين إضافيين؛ ليست 102 ضغطة.

مع عشرة تحديثات متحدث وheartbeat طبيعي في النسخة النهائية: **p95=33.6ms**، والصفوف القديمة لم تُرسم مجددًا. أقصى مؤشر إطار **147ms**، مع 13 Long Task أقصاها **344ms**؛ لا ندّعي اختفاء كل التقطيع. عينة المتحدث الأصلية كانت p95=523.6ms لكن شرط heartbeat فيها مختلف، لذلك لا نعرض منها نسبة تحسن مضبوطة. النسخة الوسيطة مع Composer فقط بلغت p95=235.2ms وأعادت 3,000 صف؛ هذا الدليل برّر الإصلاح الثاني.

تحقق الهدف المرصود p95 أقل من 50ms في هذه البيئة. الزمن مؤشر input إلى rAF، وليس INP أو عرض البكسلات، ولا يشمل انتظار الحدث قبل دخوله الخيط الرئيسي. CDP ثوانٍ تراكمية للمعالج داخل renderer، وليس نسبة CPU للجهاز. ظروف baseline واختلافاتها وفشل تنظيف fixture الأول محفوظة بلا إخفاء في [تقرير القياس](./browser-performance.md) و[شروط العينات](./artifacts/measurement-conditions.json). القياسات وصفية لبناء التطوير ولا تضمن استجابة جميع الأجهزة أو الإنتاج.

فشل اختبارا انحدار قبل الإصلاح بسبب إعادة رسم المؤلفين، ثم نجحا بعده. تشغيل baseline للمتصفح حفظ قياسه ثم فشل تنظيف طلب fixture معلّق؛ وأُوقف اختبار ضغط متحدث بمؤقت غير متوازن. هذه ليست تشغيلات قبول ناجحة، ولا أعطال منتج مثبتة، واحتُفظ بتفصيلها في تقرير القياس. لا تُستبدل أي من النتائج النهائية بنتيجة Cache.

اختبارات القبول تثبت 100 حرف سريع، 760 حرفًا عربيًا، اللصق والحذف وإدخال النص في منتصفه، IME عبر CDP، حفظ النص والتركيز والمؤشر مع وصول رسالة ودخول مالك أثناء الكتابة وحركة CSS فعلية، ثم POST واحد وظهور الرسالة مرة واحدة. نجاح الإرسال من الواجهة لا يثبت idempotency بعد إعادة محاولة طلب انتهت مهلته؛ لم نغيّر هذا العقد. راجع [تدقيق النقل](./socket-audit.md).

راجعت QA والمنسق الصور، واجتازت المقاعد والأدوات فحوص 390×844 و1440×900 وتكبير النص 200% دون تداخل أو تمدد في العناصر المقاسة. فتح وإغلاق لوحة المفاتيح جرى بمحاكاة visualViewport مع حفظ التركيز والمسودة. الصور والقياسات في [تقرير QA](./qa.md).

نجحت ESLint للملفات المعدلة، وفحص أنواع web وتبعياته، وبناء Next.js للإنتاج وفحوص التعرض العام وميزانية CSS، والتنسيق وgit diff --check. نُفذت بعد دمج التعديل، ولم تتغير بصمة المصدر بعد القياس.

## غير المنفذ والمخاطر المتبقية

- Safari/WebKit، وأجهزة Android/iOS الفعلية، ولوحة مفاتيح نظام جوال فعلية: غير متاحة، وغير منفذة.
- الكتابة مع ميكروفون وصوت SFU حقيقيين: غير منفذة. اختُبرت واجهة غير مكتومة وAudioSession محاكى، فلا يصح تسميتها تحققًا صوتيًا حقيقيًا.
- بقيت مهام خلفية طويلة في بناء التطوير؛ لم نثبت زوالها في التطبيق المنشور أو في كل مزودي المؤثرات في shell الكامل. لم نغير المؤثرات أو الصوت بسبب افتراض غير مثبت.
- لم نُعد اختبارات تحميل SFU أو التكامل المرتبطة بخدمات خارجية لهذه المراجعة؛ تشغيلها السابق ليس اختبارًا جديدًا لهذا التعديل.
